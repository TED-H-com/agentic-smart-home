# 設備探索與接入

2026-10-16 Owner steering：單一家庭的經驗用來改善通用產品設計。智能管家應協助使用者建立設備清單、辨識可用的接入方式、完成必要設定，並確認實際可用的功能；產品不以某個品牌組合或特定路由器作為前提。

這項方向補充並取代 [Plan v3](v3/PROJECT_PLAN_V3.md) 首輪暫緩「整屋自動探索」的安排。六份原稿維持不變；探索能力分段交付，實體設備與現場網路驗收仍屬 E3，不能因新增清單或程式測試而升級原有 [32 項驗收](v3/PILOT_ACCEPTANCE.md)。

## 產品體驗

使用者可以請管家「看看有哪些設備可以接進來」。系統先使用目前已可讀取的來源，呈現已知設備、可設定的整合和仍缺少的資訊。需要帳號、掃碼或實體配對時，才在對應步驟引導使用者完成。重新整理或服務中斷後，應能分辨哪些是現有設定、哪些仍待處理，以及哪些結果需要重新確認。

完整流程為：取得觀測 → 合併與辨識 → 提出接入建議 → 原生設定與授權 → 核對能力 → 持續觀測。每一步都可以有部分成果；某個來源不可用，不應隱藏其他來源已取得的資訊。空清單必須附帶探索範圍，不能解讀為家裡沒有設備。

日常控制仍使用 Home Assistant。設備探索是初始化與後續新增設備的協助能力，沿用同一 Controller、身份、對話與家庭政策，不另建一個家庭控制平臺。

## 首個工程切片

本輪範圍是唯讀的 `GET /api/discovery` 與現有設備頁的精簡探索區塊。只限目前有效的 Owner 讀取，使用 Controller 既有 HA 連線取得快照；不讓模型指定網段、路由器位址或管理 API。

| 來源 | 本輪取得的資訊 | 結果界線 |
|---|---|---|
| HA 待設定探索流程 | HA 已建立、等待原生設定的探索候選 | 不等於所有 LAN 設備，也不代表整合已設定 |
| HA integration entries | 已設定的整合及其回報狀態 | `loaded` 不等於所有設備在線或每個功能已驗證 |
| HA device registry | HA 記錄的設備及其關係 | 可能包含服務或邏輯設備，不一律計為實體設備 |
| HA entity registry | 實體所屬設備與停用標記，用於設備功能計數 | 沒有當前 state 不代表實體不存在 |
| HA states | 本次 HA 狀態的可用性，用於設備功能計數 | 是 HA API 的觀測，不是物理動作證明 |

來源獨立回報成功、不可用或不支援；一個來源失敗時，其他有效結果仍可顯示。未知必要格式或不支援的上游命令只停用對應來源，不能把錯誤變成成功的空清單。來源失敗時，依賴它的關係或結論也必須標示未確認。

這一版只做即時快照，不新增持久資料格式、背景掃描或長期設備歷史。Web 可重新整理並交接到固定的 HA 原生整合設定入口。開啟原生頁面不代表已開始或完成設定；回來後重新讀取來源才能更新觀測。原生頁面仍需要 HA 自己的有效登入。

路由器／防火牆清單、直接 LAN 探索、品牌 Hub 或雲端帳號的獨立收集器，都明示為尚未實作。HA 已接入的 Hub／帳號設備可能出現在 HA registry，這不等於產品已直接連接該 Hub 或帳號。

本輪不增加 MCP 工具或模型可讀範圍，不自動啟動、提交或刪除 HA config flow，不安裝整合，不改家庭權限，不呼叫設備服務。現有 `home.observe` 的政策範圍保持有效。後續對話式探索須另做有範圍的資料分享與工具契約，不能直接把完整清單送進模型。

## 當次探索帶入對話（D3a 工程切片）

正式智能管家新增「分享探索結果」，外層 Web 與 HA 側欄都能使用。開啟後才讀取當次 HA 快照，由 Owner 從待設定候選、已登錄設備或已設定整合中選取最多八項；預設不選任何項目。畫面呈現包含原草稿在內的完整對話預覽，按「帶入對話」只填入可編輯草稿，仍須按原有「送出」才分享給管家。整則訊息上限沿用 5,000 字，不截斷後偷偷送出。

這是一段普通訊息中的歷史觀測，不建立持續讀取權限或新的 MCP 工具。文字包含當次時間、所選項目的必要欄位及相關來源的狀態／時間；不帶未選設備的父子關係 ID、整合 ID、全家庭筆數或摘要。名稱與上游文字以資料欄位處理。重新讀取清除舊選取與預覽；切換對話、身份失效或關閉視窗後，晚到回應不能填回草稿。取消選取不會撤回已送出的對話內容；保存、身份與政策變更沿用既有對話規則。

HA 側欄僅新增精確的 `GET /api/discovery`，必須通過既有 Ingress 身份、配對、Host 能力與即時 HA Owner 驗證；讀取完成後再次核對身份、家庭憑證及 Web 世代。這不開放任意路徑、設定 POST 或模型自動查詢。資料庫格式、聊天 API、MCP 工具與家庭讀寫 policy 均不改變。

使用者可從固定原生整合設定入口完成登入或配對，再回來重新讀取並選取新的資料。候選消失不代表設定完成；新設備不自動分享給 AI，也不因這段訊息取得控制權。本切片不提供管家自主掃描、可接續的品牌設定工作或逐能力實體驗證。D2、完整 D3 與 D4 繼續按下方分段交付；既有 0.9.0 安裝媒體尚未包含此增量。

## 觀測與設備身份

後續來源都應透過獨立 adapter 產生有界、可核對的觀測，接入同一份探索結果，而不是為每個品牌另建一套流程。概念上區分以下對象：

| 對象 | 含義 | 關係與合併規則 |
|---|---|---|
| 網路端點 | 某個網路範圍內的位址或服務 | IP 可變動；端點不必然對應單一實體設備 |
| 設備紀錄 | HA、Hub 或帳號來源認定的一個設備 | 保留來源命名空間；跨來源合併需要可核對的身份證據 |
| HA entity | 設備或邏輯功能的一個可觀測／控制項目 | 多個 entities 可以屬於同一設備，也可能沒有 device registry 紀錄 |
| 整合／帳號 | 負責接入一組設備的設定 | 同一整合可有多個設定實例，不能只依 domain 合併 |
| 探索候選 | HA 或其他來源建議進行設定的對象 | 尚未設定的候選不能當成已接通的設備 |

首版以 HA 自己的設備、實體與整合 ID 連接資料；流程 ID 只識別當前流程，不保證是永久設備身份。不以相同名稱、型號、IP 或 MAC 廠商名稱自行合併。Hub 與其子設備是父子關係，不能因共享網路出口而合成一台。沒有 state 的設備仍列於設備快照；沒有 state 的 registry entity 仍計入所屬設備的功能數。沒有 device 的 entity 計入來源筆數及摘要 digest，本版不另列這些 entity；獨立呈現留待後續。未知關係和多個同品牌設定保持分開。

每份觀測要能回答「從哪裡、用什麼方法、在什麼時間、讀到哪個對象」。來源 adapter 的版本／契約、收集時間、來源本身提供的時間、可用範圍與限制應分開記錄。後續保存或分享證據時，沿用 [現行規格](../PROJECT_SPEC.md) 的來源、摘要 digest、去密與保存期限要求。

讀取時間只證明這次成功詢問來源。DHCP 租約、registry 紀錄、雲端資料及 HA state 各有自己的更新方式；不能把本次查詢時間當作設備剛剛在線的時間。若來源沒有提供設備新鮮度，應標示未知。首版快照不提供跨重啟的 last-seen 或歷史離線判斷；刷新失敗也不能把舊畫面重新標成剛完成的成功觀測。

## 辨識、建議、授權與驗證

這些是獨立資訊，不能只用一條持續往前的「完成度」表示：

| 維度 | 可以宣稱的事實 | 不能據此推論 |
|---|---|---|
| 已觀測 | 某來源回報了端點、紀錄或候選 | 品牌／型號已確定、目前在線 |
| 已辨識 | 有來源及理由支持某個身份或類型 | 必定有可用整合或已授權 |
| 建議接入 | 有證據支持某個整合選項或 HA 已提供候選 | 設定成功、所有功能皆支援 |
| 已授權 | 目前身份與授權允許特定讀取、設定或動作 | 永久有效、可擴大到其他設備／操作 |
| 已驗證 | 指定時間、方法與範圍的檢查通過 | 其他功能、物理結果或未來狀態也已通過 |

首版採 HA 已提供的整合關係與探索候選，不另外猜測品牌支援程度。未來的指紋辨識必須附理由與證據強度；廠商 OUI 或主機名稱只是提示，不能單獨當成確定型號。無法合併或證據衝突時保留多個候選，讓後續來源補證。

驗證至少要分開「整合設定已存在」「HA 可讀取狀態」「特定能力可用」和「實體動作已確認」。API state 讀取不能升級為實體設備驗收。授權撤銷、來源變舊、整合卸載或設備失聯後，先前的驗證紀錄仍是歷史事實，卻不能繼續代表當前可用。

原生 HA 登入與配對、模型讀取資料的範圍、Controller 家庭寫入權限是不同授權。探索結果不會替使用者授權任何一項。後續動作驗證沿用既有精確提案、批准與讀回機制，並先確認所測功能及目標設備。

## Adapter 與信任邊界

所有設備名稱、服務宣告、廠商文字與來源回應都當成不可信資料。只投影需要的欄位、限制大小、以文字顯示；不回傳完整 config entry 設定、秘密、OAuth 資料或完整 flow context。原生設定連結由產品固定產生，不採用設備回報或模型生成的任意 URL。

HA registry 與 config flow 接點的相容性由獨立 adapter 檢查。不能因使用 REST／WebSocket transport，就宣稱其中每個內部命令都是永遠相容的公開介面。新增欄位可忽略；缺少必要語意時顯示來源不支援或不可用。詳見 [adapter 邊界](ADAPTERS.md)。

後續路由器、Hub 和帳號 adapter 只取得對應來源需要的權限，憑證由受信任服務保管。直接 LAN 收集應有明確的網路範圍、固定方法、期限及速率限制；不把任意掃描或 shell 交給 Hermes／workers。來源文字不能變成新的工具權限或執行指令。

目前受管 HAOS 使用 NAT，未提供家庭 LAN multicast 探索；本輪不修改網路。HA 能讀到多少候選受其實際網路與已啟用整合影響；不能保證空白家庭初始化就能看見全屋設備。網路覆蓋與日後可用的接法須另外驗證，見 [Linux 網路限制](LINUX_PRODUCT.md)。

## 分段交付與驗收

| 階段 | 交付範圍 | 必須取得的證據 |
|---|---|---|
| D1：HA 探索快照 | Owner 唯讀 API、分來源狀態、既有設備頁提示、固定原生交接 | 合成資料與協定測試、身份／去密／降級測試、編譯介面測試；真 Core 相容性另記 |
| D2：多來源盤點 | 可插拔路由器／LAN／Hub／帳號來源、覆蓋範圍、來源身份與新鮮度 | 每個 adapter 的真實來源測試、同名不同設備與同設備多來源案例、斷線與資料過期案例 |
| D3：對話引導接入 | 有範圍的探索工具、必要登入／配對交接、可接續的設定進度 | 真帳號流程、撤權與中斷恢復、既有設定保留、不重複提交或誤認完成 |
| D4：逐能力驗證與持續盤點 | 分別確認讀取／控制能力，呈現新增、移除與需重新確認的項目 | 授權的實體設備測試、離線與恢復、觀測期限、E3 現場與長時間證據 |

D1 的必要案例包括：

- 空快照、未連接 HA 與某一來源失敗，均呈現實際範圍；其他來源不被一併清空。
- 多個同 domain 整合、同名設備與 Hub 子設備不被錯誤合併；無 state 的 registry entity 仍納入功能數，沒有 device 的 entity 仍計入來源筆數／digest，但不虛構所屬設備或獨立呈現。
- 待設定流程只形成候選；被忽略、完成或消失的流程以重新讀取結果為準，不以產品自己啟動流程補齊。
- 惡意名稱、額外欄位、畸形必要欄位、超量回應與含秘密的 flow context，不形成腳本、外部導航或未經投影的輸出。
- 非 Owner、失效身份與讀取期間撤權不能取得家庭快照；新增唯讀 API 不擴大 MCP 或家庭 policy。
- 讀取、刷新與原生交接不發出 HA 設定／設備寫入；不把 `loaded`、有 state 或已有設定呈現為物理驗證。

工程測試、真 Core／HAOS、真帳號和實體設備結果分開登錄於 [進度](v3/PROGRESS.md) 與相應證據。D1 完成只代表上述唯讀切片可用；完整對話接入、多來源掃描與整屋跑通仍按後續階段驗收。

# 設備探索與接入

2026-10-16 Owner steering：單一家庭的經驗用來改善通用產品設計。智能管家應協助使用者建立設備清單、辨識可用的接入方式、完成必要設定，並確認實際可用的功能；產品不以某個品牌組合或特定路由器作為前提。

這項方向補充並取代 [Plan v3](v3/PROJECT_PLAN_V3.md) 首輪暫緩「整屋自動探索」的安排。六份原稿維持不變；探索能力分段交付，實體設備與現場網路驗收仍屬 E3，不能因新增清單或程式測試而升級原有 [32 項驗收](v3/PILOT_ACCEPTANCE.md)。

## 產品體驗

使用者可以請管家「看看有哪些設備可以接進來」。系統先使用目前已可讀取的來源，呈現已知設備、可設定的整合和仍缺少的資訊。需要帳號、掃碼或實體配對時，才在對應步驟引導使用者完成。重新整理或服務中斷後，應能分辨哪些是現有設定、哪些仍待處理，以及哪些結果需要重新確認。

完整流程為：取得觀測 → 合併與辨識 → 提出接入建議 → 原生設定與授權 → 核對能力 → 持續觀測。每一步都可以有部分成果；某個來源不可用，不應隱藏其他來源已取得的資訊。空清單必須附帶探索範圍，不能解讀為家裡沒有設備。

日常控制仍使用 Home Assistant。設備探索是初始化與後續新增設備的協助能力，沿用同一 Controller、身份、對話與家庭政策，不另建一個家庭控制平臺。

既有的多來源盤點與接入追蹤由 0.10.0 工程預覽交付；精確 ISO、公開 App 與下載驗證結果見 [驗證紀錄](VERIFICATION.md)。0.9.0 ISO 不包含它們，公開示範仍使用虛構資料，真帳號及實體設備另行驗收。

### 對話中的唯讀探索

管家可透過 `home.discover` 協助「找看看有哪些設備還沒接好」。尚未分享這次探索時，工具只回傳「探索家庭設備」操作卡，不讀取家庭資料。舊 API 的 `discover_devices: true` 仍只分享最多八個 HA 探索候選。新介面明示分享環境後，同一則訊息額外帶 `discover_environment: true`：分享 HA 已登錄設備、已設定服務、保存的區網觀測與當前家庭連線診斷；設備／服務／網路觀測各最多十六項，混合候選最多八項。位址、MAC、原始匯入內容與可辨識的憑證不進這份模型投影。此選擇不沿用到下一則訊息，模型不能透過工具參數自行同意。

探索不要求先授予任何設備控制權限，因此空的家庭授權清單不會阻止找設備。結果與部分、失敗或截短的來源一同呈現在對話；未取得完整來源時，候選總數維持未知。空結果不能解讀為家裡沒有設備。IPP、Synology DSM、Matter、Home Connect 等顯示易懂的種類名稱，但不根據種類推測特定品牌、型號或實體功能。

這個工具使用既有唯讀 adapter，不自行發送 LAN 掃描，也不分享設定密碼欄位或 entity state。Owner 可在聊天中另外按「探索更多設備」，選定家庭網路並確認；只有此操作呼叫既有有界收集器，完成後再分享結果。Controller 在讀取前後及 MCP 回應落盤等待後重新檢查原本的對話範圍、HA 連線、即時 Owner，以及已分享盤點的版本與有效期限。

唯讀探索本身不增加家庭讀取／控制授權，也不建立 HA config flow。分享過的快照是普通對話內容，沿用原有身份與保存期限；下一則訊息未同意新的探索，不會撤回已分享的內容。保存的區網觀測依原始來源時間判斷過期，讀取不更新觀測時鐘；無 HA 候選但有區網紀錄時，管家仍能提出具體線索，不能將其說成已接入設備。

### 聊天內接通家庭網路（未發行）

主機的智能管家提供「接通家庭網路」。展開先讀取目前狀態；本人按「連上家庭網路」後，沿用既有還原點、正常關機、有線接入、開機及讀回流程。多張有線網卡仍需明確選擇；畫面會先說明家庭自動化暫停。打開卡片或讀取狀態不代表批准接入。

瀏覽器在送出前，只將工作識別碼保存到目前登入範圍的 `sessionStorage`。同一分頁重新整理或切換畫面後，以 `GET /api/host/jobs/{id}` 精確讀取；回應遺失、找不到原工作或讀取失敗時保留待確認狀態，不再提交。無法保存識別碼時不開始接入。關閉分頁、清除瀏覽器資料或更換登入範圍後，不保證自動找回；工作本身仍由 Host 保存。舊卡片與識別碼不提供登入權限。

「繼續探索家庭設備」在按下時重新讀取家庭狀態，只有新鮮的 Core-ready 證據且沒有進行中、不明或待復原工作才繼續。按鈕旁先說明會分享設備名稱、已保存盤點與家庭連線狀態；本人按下後才將探索請求交給管家，保留原聊天草稿。接入完成本身不觸發分享，也不自動啟動區網掃描。guest 位址、探索設定就緒與實體設備驗收仍分開呈現。

HA 側欄只提供回到主機桌面的操作指引，沒有 Host 管理權限。這是未發行增量，不表示既有媒體已包含此介面，亦不代替實體家庭驗收。

### 聊天內確認接入 IPP 印表機

目前可直接執行的第一條接入路徑是 Core `2026.10.1`／`2026.10.2` 已發現的 IPP `zeroconf_confirm` 空表單。版本使用精確白名單；其他 patch／預覽版仍需另外驗證。這是窄範圍的原生設定 adapter；不接受任意網址、表單欄位、帳密或模型提供的核准，也不擴大到未知版本／品牌的配對。

1. Owner 在當前對話選擇具體印表機。Controller 重新核對 HA Owner、連線、原始探索身分及確認表單，保存有期限的提案。
2. 聊天顯示設備、操作與備份範圍；Owner 按「確認接入」後，綁定提案摘要與版本。API 先保存工作再回傳，畫面讀取同一份進度。
3. 固定服務建立並讀回 Supervisor 的 Home Assistant 設定備份，保存 Controller 快照，再確認原探索及既有設定沒有改變，才提交該空表單。模型不持有管理憑證。
4. 讀回精確建立的整合及關聯設備／功能狀態。「設定已保存」不代表實體功能已驗證；不送出列印作業，也不自動授予 AI 控制權限。
5. 登出、暫停、更新或來源改變會在送出邊界阻止新操作。可能已送出但回應遺失的情況，只核對原生設備身分與新整合，不重播接入請求。尚未送出的準備失敗可以重新提案。

接著聊天、重新整理或側欄暫時斷線不會丟失已受理的進度；舊卡片可以讀取結果，但不能作為新的接入批准。側欄背景工作會持續核對原 Owner 與配對，撤銷則停止對應工作。相同 Owner／家庭連線更換登入憑證後，仍可讀回及核對舊結果；尚未執行的提案必須重新檢查並批准，不沿用舊憑證的執行授權。

入口為 `/api/device-setups`、`/{id}`、`/{id}/approve`、`/{id}/input`（Synology 多步輸入）與 `/{id}/reconcile`。寫入需要既有 Owner／CSRF（或已驗證 Ingress）和 Idempotency-Key。私有 `device_setup_v1` 紀錄在 schema 3 中可由舊版忽略；舊版不能續跑這些工作。內容依保存期限移除設備名稱，保留有界的操作身分與不確定結果防重播紀錄。備份範圍是 HA 設定，不是整台主機回復。

Adapter 依固定上游來源核對：[IPP config flow](https://github.com/home-assistant/core/blob/2026.10.1/homeassistant/components/ipp/config_flow.py)、[flow HTTP adapter](https://github.com/home-assistant/core/blob/2026.10.1/homeassistant/helpers/data_entry_flow.py)、[IPP device identity](https://github.com/home-assistant/core/blob/2026.10.1/homeassistant/components/ipp/coordinator.py)。這些私人前端 API 的相容性限制只停用相關接入能力。

其他候選仍提供來源與下一步、原生配對或既有接入追蹤；目前不宣稱所有品牌均可在聊天內接入。合成設備、HTTP／WebSocket 協定測試與瀏覽器測試不代表實機驗收；真實印表機、HAOS 備份還原及現場使用仍需各自驗證。

### 聊天內確認接入 Shelly 1

第二條接入路徑沿用上述提案、本人確認、備份、持久化工作與精確讀回，限於 Core `2026.10.1`／`2026.10.2` 已存在的 Shelly `zeroconf` → `confirm_discovery` 空表單。Controller 必須核對原生表單回報型號恰為 `Shelly 1`，並以正規化的 MAC、整合種類及原流程綁定提案。聊天先「核對型號」，其他型號、需要密碼、藍牙配對或未知步驟改由固定的原生家庭設定入口處理；保存的網路線索不能批准接入。

這是**原生回報型號的限定**，不是實體世代鑑定。已審閱版本的 `SHSW-1` 對應 `Shelly 1`，但上游對未知型號會直接顯示回報字串；因此不能把這個欄位當成不可偽造的 Gen1 證明。批准文案包含原生整合可能設定設備連線、備份只涵蓋 HA 設定；Controller 不發送繼電器切換，也不授予 AI 控制權限。RPC 裝置的原生初始化可能設定 outbound WebSocket 或停止它的藍牙掃描腳本，本輪的 Gen1 協定驗證不能擴張為所有 Shelly 的零設備寫入保證。

遺失確認回應時，恢復只讀取新整合及原生設備登錄：必須有相同 Shelly MAC 識別及精確整合成員關係，不能憑名稱、IP、候選消失或另一個 domain 的同值識別碼判定完成。既有 IPP 紀錄繼續可讀；新寫入的私有接入紀錄版本為 2，舊 v1 IPP 紀錄在該筆紀錄下一次寫入時轉為 v2，保存原提案摘要與工作身分。舊 binary 對未知紀錄停止新接入寫入，不能宣稱可以無條件降版後繼續操作。

候選的可選 `confirmation_step` 只由唯讀探索投影三個已知步驟（IPP、Shelly 的確認步驟與 Synology 的 `link` 登入步驟），用於介面導向，不是批准或可執行能力證明；執行前仍重新核對精確 Core、型號、表單、Owner 與原提案。分享給管家的設備名稱會遮去連續十二位十六進位的 MAC 名稱後綴，和原有含分隔符的位址一致。

上游邊界見固定版本 [Shelly 設定流程](https://github.com/home-assistant/core/blob/2026.10.2/homeassistant/components/shelly/config_flow.py)、[設備登錄與初始化](https://github.com/home-assistant/core/blob/2026.10.2/homeassistant/components/shelly/coordinator.py) 及 [aioshelly 13.34.1](https://github.com/home-assistant-libs/aioshelly/tree/13.34.1)。Synology NAS 改用下方獨立的多步 adapter，不當作空表單接入。

### 聊天內輸入帳號接入 Synology NAS

第三條接入路徑支援 Core `2026.10.1`／`2026.10.2` 已發現的 Synology NAS（`synology_dsm`，SSDP 或 zeroconf 來源、原生 `link` 步驟、12 位序號身分）。流程沿用提案、本人確認、備份與精確讀回，再加上多步輸入：接入卡顯示說明與「NAS 帳號／NAS 密碼」欄位，按「登入並接入」即為批准；Controller 先完成家庭設定備份，再送出原生登入步驟。帳號開啟兩步驟驗證時，接著輸入驗證器 App 顯示的驗證碼；最後從 NAS 回報的共用資料夾選擇家庭備份位置，資料夾內路徑沿用原生預設值。多步輸入使用 `/api/device-setups/{id}/input`。

帳號、密碼與驗證碼只在接入卡輸入，經單次 Owner 請求交給 Controller 轉送原生流程；不寫入 Controller 資料庫、接入紀錄、請求收據、快照或證據，送出後立即清空欄位，遺失回應時不保留重送內容。管家只看得到目前步驟，不能代為輸入或送出，也不因此取得 AI 控制權限。NAS 在通過兩步驟驗證後會記住這台家庭系統；登入資料由 HA 原生整合依其既有方式保存。

後續每一步送出前先持久化並重新檢查 Owner、AI 暫停、主機更新，以及家庭設定沒有出現其他新的 NAS 連線；未通過時顯示「這一步沒有送出」，須先重新讀取。送出後回應遺失或結果不明時只讀回：原流程仍停在同一步就重新開放輸入；流程已結束時，以 NAS 網卡 MAC 比對新整合的原生設備登錄，無法確認則維持待確認，不重送帳密或驗證碼。DSM 登入後會以實際回應的 NAS 序號建立整合，所以即使收到原生建立結果，也必須在設備登錄看到探索時的 NAS 網卡 MAC 屬於這筆新整合，才顯示接入完成；同一位址換成另一台 NAS 時維持待確認。每步輸入 30 分鐘內有效，逾時後重新讀取即可繼續；一次接入最多送出 8 步，達到上限即停止，可重新準備新的接入（需要再次確認與備份）。

NAS 若早已接入，原生流程會以新輸入的帳號更新原連線（`reconfigure_successful`）；聊天如實說明「已用你輸入的帳號更新原有連線」，不宣稱建立新整合，也不推測是哪一筆。原生流程在重新登入出錯時會回到含預設值的完整設定表單，聊天不讀取也不保存該表單，改由固定的原生家庭設定入口完成。

登入沿用原生預設：HTTPS、預設連接埠 5001、不驗證 NAS 自簽憑證，以及原生預設備份路徑；聊天不支援自訂連接埠。多網卡或同網段多台 NAS 的實機情境，以及真實 DSM 韌體的受信任裝置與過期驗證碼行為尚未驗證。新寫入的 Synology 接入紀錄為版本 3；IPP／Shelly 維持版本 2，保存欄位與前一版相同。舊 binary 遇到未知紀錄停止新接入寫入。上游邊界見固定版本 [Synology 設定流程](https://github.com/home-assistant/core/blob/2026.10.2/homeassistant/components/synology_dsm/config_flow.py)。

### 換對話後續接與解讀結果

聊天的「設備接入進度」在展開時讀取保存清單。Owner 明確選定一筆後，才讀回該工作的最新狀態；不因開啟、切換對話或重新整理而重送批准。歷史入口可以核對結果不明的原工作，不提供新的接入批准。

「請管家解讀結果」以當前 Web／Hermes 訊息的 `device_setup_id` 分享精確一筆紀錄，保留原草稿。`home.device_setup_status` 不接受模型參數，只能讀取這次訊息選定的工作。它重新確認 Owner、家庭連線、對話／側欄授權及紀錄版本，回傳經去密的摘要與最多十六筆關聯設備；不提供批准、備份識別或任意家庭 API 存取。

已完成的接入是歷史事實，目前整合是否存在、是否載入及功能狀態是否可讀取則來自這次觀測。來源失敗或截短保留未知／範圍限制；不以舊成功紀錄推定目前可用，也不當成實體功能驗證。未在當前訊息選定工作時，工具只說明如何分享，不讀取清單。後續訊息不繼承新的讀取授權；已分享摘要仍依原本的對話保存政策保留。

只更新 Controller 的既有安裝可能仍使用較舊的管家映像。送出這類解讀前，Controller 先確認 runtime 實際宣告 `home.device_setup_status`；沒有這項工具時，不送出模型工作，直接說明版本限制，保留進度查閱與一般對話。此檢查不切換映像、不清除登入，也不要求重新授權。

## 現行多來源流程

「探索更多設備」已接入主機 LAN 收集器與路由器／防火牆清單匯入。設備頁及管家「分享探索結果」使用同一份 Controller 盤點；Owner 選擇主機上的網路，按「開始探索」，或選取 JSON、CSV、dnsmasq leases 檔案。觀測依來源列出，附辨識理由與官方接入說明；可建立接入追蹤，到 HA 原生設定完成登入或配對，返回明確選定整合，再讀取關聯設備和狀態。選取觀測可先預覽，再帶入管家草稿。

| 取得方式 | 實際收集內容 | 涵蓋範圍 |
|---|---|---|
| 主機鄰居表 | 所選介面的 IPv4／MAC 快取 | 快取不是設備在線證明，不發送網段掃描 |
| mDNS | 固定服務類型的 PTR 回應和服務名稱；同封包、同完整 HTTP 服務實例的 Synology 廠商分類 | 有界 multicast 查詢；不保存原始 TXT 欄位，回應位址可能是服務代理，不是已核對的設備 IP |
| SSDP | M-SEARCH 回應的服務類型與有限宣告欄位 | 不下載 LOCATION、不讀設備管理頁、不抓完整描述或 TXT |
| 路由器／防火牆匯出 | JSON、CSV、dnsmasq 租約中的選定欄位 | 使用者匯入的清單；沒有登入路由器，也不持有管理憑證 |
| HA | 探索候選、整合、設備、entities 與 API 狀態 | 繼續使用既有唯讀來源，不因盤點而增加控制權限 |

主機只提供目前啟用、具實體裝置證明的 Ethernet／Wi-Fi IPv4 介面。介面識別碼由主機產生，掃描前重新核對；不接受模型或瀏覽器指定任意 IP／CIDR。每次只保存最近一次選定網路的 LAN 結果，匯入清單另外保存；新掃描取代舊 LAN 結果，新匯入取代舊匯入。虛擬 bridge、VLAN、VPN、IPv6、隔離訪客網路、休眠設備及非 IP 子設備需其他來源補足，空結果不代表全部設備已接通。

辨識規則是有版本、可審查的 adapter，依官方 HA manifest 支援 Hue、Google Cast、ESPHome、HomeKit Device、Shelly，以及下列 IPP、Synology、Matter 服務線索；匯入名稱／廠商中 Tuya、Smart Life 等線索提供帳號接入指引。Google Cast 不代表 Google Home 的全部帳號設備，品牌名稱與 MAC 不構成已確認型號。未辨識項目仍保留，可選取交給管家協助核對。不同來源不按名稱、IP 或 MAC 自動合併，列表筆數稱「觀測」，不宣稱有同樣數量的實體設備。

### 常見網路服務帶入聊天

固定收集器增加 `_ipp._tcp`、`_ipps._tcp` 與 `_matterc._udp`，沿用原本選定實體 IPv4 網路、明確確認、時間／封包／大小限制與冷卻時間。Controller 的辨識規則摘要版本為 2；保存格式與 API 契約仍為 1，舊觀測依目前規則重新投影，不重跑掃描。新增查詢需要新版 Host 收集器，僅更新 Controller 不會改變已安裝 Host 的查詢範圍。

| 線索 | 可以說明的下一步 | 不能推定的事 |
|---|---|---|
| IPP／IPPS 服務 | 核對是印表機本身或共享佇列；HA 已發現的支援候選才提供接入提案 | CUPS 可能代答；不按同名／同位址合併，不代表已裝列印服務或可列印 |
| HTTP 服務及同實例 `vendor=synology*` | 作為 Synology 儲存服務線索，依原生流程完成帳號設定 | 只保存固定 `synology` 分類；不是已核對型號、設備身分或原生設定已就緒 |
| Matter `_matterc._udp` | 說明待配對服務的可能性，依手機原生流程及配對碼核對 | 不保證設備尚未加入其他家庭；不分享配對碼，不代表 IPv6／Thread 通路已可用 |
| Matter `_matter._tcp` | 保留為運作中的服務觀測 | 不因此新增待配對建議或要求重設設備 |

Synology 的通用 HTTP 名稱、SSDP Basic 類型或品牌字樣不足以證明身分。廠商宣告須綁定同封包的精確 PTR／TXT 實例，重複或畸形 TXT 不提供分類；其他 TXT、原始值與後綴不保存。匯入清單的服務／廠商仍只是 `hint`；SSDP 未下載 XML，因此不能取得官方規則所需的廠商證據。Home Connect 不從任意家電名稱猜測，繼續使用 HA 已提供的候選。

聊天逐筆區分 HA 已發現候選與保存的網路線索，保留各類型的下一步。按「請管家核對」仍帶著所選來源與種類，不把同名線索當成同一設備。網路 IPP 線索不能直接批准接入；後端仍要求精確的 HA 原生確認流程。

規則依 Core `2026.10.2` 的 [IPP manifest](https://github.com/home-assistant/core/blob/2026.10.2/homeassistant/components/ipp/manifest.json)、[Synology manifest](https://github.com/home-assistant/core/blob/2026.10.2/homeassistant/components/synology_dsm/manifest.json)、[Synology 設定流程](https://github.com/home-assistant/core/blob/2026.10.2/homeassistant/components/synology_dsm/config_flow.py) 及 [Matter manifest](https://github.com/home-assistant/core/blob/2026.10.2/homeassistant/components/matter/manifest.json) 核對；服務語意另見 [Matter 探索](https://github.com/project-chip/connectedhomeip/blob/master/docs/tips_and_troubleshooting/discovery_from_a_host_computer.md) 與 [CUPS 共享](https://openprinting.github.io/cups/doc/sharing.html)。合成封包／聊天驗證不能代替實際家中探索與配對。

### 第一次家庭接入

首次可從一組 Hue 或 Tuya／Smart Life 開始：先確認觀測來源，再建立接入追蹤；在 HA 原生設定完成橋接器配對或帳號授權，返回明確選取整合、讀回設備／功能，最後由使用者確認指定低風險設備的實體動作。這幾步分別記錄，不能由 `loaded` 或一筆 API state 推成物理驗證。

Google Cast 線索只涵蓋 Cast 接入，不代表讀到 Google Home 的完整帳號；產品亦未提供完整 Alexa 帳號盤點。Tuya 原生整合需要 User Code 與手機 QR 授權，上游 SDK 不保證暴露 Smart Life 的全部功能。Hue 原生整合可手動加入橋接器。官方步驟見 [Tuya](https://www.home-assistant.io/integrations/tuya/)、[Hue](https://www.home-assistant.io/integrations/hue/) 與 [Cast](https://www.home-assistant.io/integrations/cast/)。

網路盤點預設不分享給模型。選取最多八項並預覽後，只將所選名稱、服務線索、來源時間及接入建議帶入可編輯草稿；位址、MAC、未選項目和原始匯入內容不隱含送出。送出仍是獨立操作。服務文字只作資料，不產生工具權限或導航網址。

### 匯入格式

檔案最多 64 KiB，每次最多 256 列；只投影下列欄位，未知欄位不保存。JSON 可為陣列，或 `devices`／`clients`／`leases` 陣列。CSV 使用同樣欄位名稱。這是通用匯入契約，不宣稱所有廠商私有匯出格式皆可直接使用。

```json
{"devices":[{"ip":"192.168.1.20","mac":"02:00:00:00:00:20","hostname":"範例橋接器","manufacturer":"Philips Hue","services":["_hue._tcp.local."]}]}
```

- `ip`（也接受 `ip_address`／`address`）、`mac`（`mac_address`）、`hostname`（`name`）：至少提供一項。
- `manufacturer`、`model`、`services`：可選線索。CSV 多個服務以分號分隔；匯入服務欄位不當成即時服務回應。
- `last_seen`：可選、含時區 ISO 時間或 Unix 秒數。沒有提供時維持未知，不以匯入時間代替。過期線索不提供目前接入建議。
- dnsmasq 採原始五欄 `expiry mac ip hostname client-id`，只取 MAC、IP、hostname；expiry 是租約到期，不是最近在線時間。

### 保存與來源狀態

各來源保留自己的收集時間、方法、範圍、adapter 版本、筆數、摘要與限制。重新讀取保存結果不刷新來源時間。超過 24 小時的來源標示過期並停止提供接入建議；依現行內容保存期限清理，預設七天。清除盤點只清除本地觀測，保留 HA 設定與接入追蹤。Owner 或家庭授權／來源變更會隔離原盤點；同一授權範圍可跨重新登入、Controller 重啟與外層／側欄接續。

LAN 收集器在受信任 Host broker 執行，Controller 只呼叫固定 Unix 路徑。單次限時、限封包／位元組／列數，單一掃描鎖與冷卻時間限制重複操作。失敗來源獨立顯示，不把另一來源的成功當成全面成功；超量以部分結果及截短提示呈現。

本節為目前產品行為；下方 D1／D3a／D3b 段落保留各次交付背景。多來源程式、公開互動示範、真 Core 相容性、真路由器／帳號及家庭現場測試各自記錄，不能互相代替。

## 首個工程切片（D1）

以下 D1／D3a／D3b 段落保留各切片的交付範圍；目前整合行為以「現行多來源流程」為準。

本輪範圍是唯讀的 `GET /api/discovery` 與現有設備頁的精簡探索區塊。只限目前有效的 Owner 讀取，使用 Controller 既有 HA 連線取得快照；不讓模型指定網段、路由器位址或管理 API。

| 來源 | 本輪取得的資訊 | 結果界線 |
|---|---|---|
| HA 待設定探索流程 | HA 已建立、等待原生設定的探索候選 | 不等於所有 LAN 設備，也不代表整合已設定 |
| HA integration entries | 已設定的整合及其回報狀態 | `loaded` 不等於所有設備在線或每個功能已驗證 |
| HA device registry | HA 記錄的設備及其關係 | 可能包含服務或邏輯設備，不一律計為實體設備 |
| HA entity registry | 實體所屬設備與停用標記，用於設備功能計數 | 沒有當前 state 不代表實體不存在 |
| HA states | 本次 HA 狀態的可用性，用於設備功能計數 | 是 HA API 的觀測，不是物理動作證明 |

來源獨立回報成功、不可用或不支援；一個來源失敗時，其他有效結果仍可顯示。未知必要格式或不支援的上游命令只停用對應來源，不能把錯誤變成成功的空清單。來源失敗時，依賴它的關係或結論也必須標示未確認。

D1 只做即時快照，不新增持久資料格式、背景掃描或長期設備歷史；下方 D3b 再增加精簡接入追蹤。Web 可重新整理並交接到固定的 HA 原生整合設定入口。開啟原生頁面不代表已開始或完成設定；回來後重新讀取來源才能更新觀測。原生頁面仍需要 HA 自己的有效登入。

D1 交付時尚未提供路由器／防火牆清單、直接 LAN 探索、品牌 Hub 或雲端帳號的獨立收集器。現在已加入上述 LAN 與清單匯入；直接 Hub／雲端帳號收集器仍未交付。HA 已接入的 Hub／帳號設備可能出現在 HA registry，這不等於產品已直接連接該 Hub 或帳號。

本輪不增加 MCP 工具或模型可讀範圍，不自動啟動、提交或刪除 HA config flow，不安裝整合，不改家庭權限，不呼叫設備服務。現有 `home.observe` 的政策範圍保持有效。後續對話式探索須另做有範圍的資料分享與工具契約，不能直接把完整清單送進模型。

## 當次探索帶入對話（D3a 工程切片）

正式智能管家新增「分享探索結果」，外層 Web 與 HA 側欄都能使用。開啟後才讀取當次 HA 快照，由 Owner 從待設定候選、已登錄設備或已設定整合中選取最多八項；預設不選任何項目。畫面呈現包含原草稿在內的完整對話預覽，按「帶入對話」只填入可編輯草稿，仍須按原有「送出」才分享給管家。整則訊息上限沿用 5,000 字，不截斷後偷偷送出。

這是一段普通訊息中的歷史觀測，不建立持續讀取權限或新的 MCP 工具。文字包含當次時間、所選項目的必要欄位及相關來源的狀態／時間；不帶未選設備的父子關係 ID、整合 ID、全家庭筆數或摘要。名稱與上游文字以資料欄位處理。重新讀取清除舊選取與預覽；切換對話、身份失效或關閉視窗後，晚到回應不能填回草稿。取消選取不會撤回已送出的對話內容；保存、身份與政策變更沿用既有對話規則。

HA 側欄僅新增精確的 `GET /api/discovery`，必須通過既有 Ingress 身份、配對、Host 能力與即時 HA Owner 驗證；讀取完成後再次核對身份、家庭憑證及 Web 世代。這不開放任意路徑、設定 POST 或模型自動查詢。資料庫格式、聊天 API、MCP 工具與家庭讀寫 policy 均不改變。

使用者可從固定原生整合設定入口完成登入或配對，再回來重新讀取並選取新的資料。候選消失不代表設定完成；新設備不自動分享給 AI，也不因這段訊息取得控制權。本切片不提供管家自主掃描、可接續的品牌設定工作或逐能力實體驗證。後續多來源與接續追蹤已由本頁現行流程及 D3b 補上；自主接入與 D4 持續觀測仍按下方驗收；既有 0.9.0 安裝媒體尚未包含此增量。

## 可接續的接入追蹤（D3b 工程切片）

設備頁與管家「分享探索結果」內提供折疊的「接入進度」。展開後才讀取保存的追蹤；Owner 對當前候選按「追蹤接入」，Controller 重新核對候選後保存名稱、整合類型、觀測時間與當時已知的同類型整合 ID。使用者經固定 `/config/integrations` 入口完成 HA 原生登入／配對，再回來讀取結果。這個追蹤區不啟動、提交或刪除 HA 設定流程；目前支援的聊天內接入另見上方 IPP、Shelly 1 與 Synology NAS 流程。

回來後由 Owner 明確選定一個同類型的整合實例，即使只有一項也不預選。名稱相同時顯示必要識別碼；追蹤建立後首次看到的實例不等於由這次操作建立。起始來源不完整時，「原本是否存在」保持未知。候選消失只表示本次未見，不顯示設定成功。

讀回分成整合紀錄、該整合關聯的登錄設備，以及這些設備的 HA 功能／可用狀態筆數。功能數沿用 device registry 的關聯，可能包括同設備其他整合的 entities；沒有 device 的 entities 不納入，不能當作整合的全部功能測試。來源不可用或截斷時，受影響總數為未知；整合不存在時不展示其歷史設備作為當前結果。設備列表與整合選項各至多 100 筆，完整來源的總數仍以全部相關設備計算。物理驗證一直明示尚未進行。

追蹤保存在 Controller，可於同一 Owner／家庭授權的外層與側欄、重新整理或重啟後接續。帳號、HA 位址或家庭 token 變更會隔離原追蹤，不能自動搬到另一個家庭；一般登入世代改變不刪除追蹤，但在途回應仍須通過即時身份檢查。每個授權範圍最多 20 筆，沿用對話內容保存期限（預設 7 天），以建立時間計算，讀取即過濾到期資料。忘記追蹤只刪除本地紀錄，不移除 HA 整合。

API 為 `GET/POST /api/discovery/setups`、`GET /api/discovery/setups/{id}`，以及精確 `POST .../{id}/select`、`POST .../{id}/forget`。修改需要既有身份／CSRF、Idempotency-Key 與選取／忘記時的 revision；紀錄和去重收據同一交易保存，回應前等待落盤並再次檢查 Owner／會話／bridge authority。Ingress 只加入上述精確路徑。沒有新 MCP 工具、HA 設定寫入或家庭 policy 授權。

只有精簡候選與選擇資料持久保存，不保存整屋快照或秘密；當前設備每次重新向 HA 讀取。私有 `discovery_setup` v1 record 不改 SQL schema 3；舊 binary 的忽略與清理限制見 [發行邊界](RELEASE_POLICY.md)。分享仍由使用者返回分享畫面、選取新的快照並送出；追蹤不自動傳給模型。

公開示範沿用真產品介面，HA 設定與觀測使用同一份虛構家庭記憶體資料；重載示範會重設，不能當成 Controller 磁碟恢復證據。D3b 交付接續與讀回，現在亦支援上方多來源候選；真品牌帳號、逐能力物理測試及既有 ISO 更新仍需各自驗證。

## 觀測與設備身份

現行與後續來源都透過獨立 adapter 產生有界、可核對的觀測，接入同一份探索結果，而不是為每個品牌另建一套流程。概念上區分以下對象：

| 對象 | 含義 | 關係與合併規則 |
|---|---|---|
| 網路端點 | 某個網路範圍內的位址或服務 | IP 可變動；端點不必然對應單一實體設備 |
| 設備紀錄 | HA、Hub 或帳號來源認定的一個設備 | 保留來源命名空間；跨來源合併需要可核對的身份證據 |
| HA entity | 設備或邏輯功能的一個可觀測／控制項目 | 多個 entities 可以屬於同一設備，也可能沒有 device registry 紀錄 |
| 整合／帳號 | 負責接入一組設備的設定 | 同一整合可有多個設定實例，不能只依 domain 合併 |
| 探索候選 | HA 或其他來源建議進行設定的對象 | 尚未設定的候選不能當成已接通的設備 |

首版以 HA 自己的設備、實體與整合 ID 連接資料；流程 ID 只識別當前流程，不保證是永久設備身份。不以相同名稱、型號、IP 或 MAC 廠商名稱自行合併。Hub 與其子設備是父子關係，不能因共享網路出口而合成一台。沒有 state 的設備仍列於設備快照；沒有 state 的 registry entity 仍計入所屬設備的功能數。沒有 device 的 entity 計入來源筆數及摘要 digest，本版不另列這些 entity；獨立呈現留待後續。未知關係和多個同品牌設定保持分開。

每份觀測要能回答「從哪裡、用什麼方法、在什麼時間、讀到哪個對象」。來源 adapter 的版本／契約、收集時間、來源本身提供的時間、可用範圍與限制應分開記錄。後續保存或分享證據時，沿用 [現行規格](../PROJECT_SPEC.md) 的來源、摘要 digest、去密與保存期限要求。

讀取時間只證明這次成功詢問來源。DHCP 租約、registry 紀錄、雲端資料及 HA state 各有自己的更新方式；不能把本次查詢時間當作設備剛剛在線的時間。若來源沒有提供設備新鮮度，應標示未知。首版快照不提供跨重啟的 last-seen 或歷史離線判斷；刷新失敗也不能把舊畫面重新標成剛完成的成功觀測。

## 辨識、建議、授權與驗證

這些是獨立資訊，不能只用一條持續往前的「完成度」表示：

| 維度 | 可以宣稱的事實 | 不能據此推論 |
|---|---|---|
| 已觀測 | 某來源回報了端點、紀錄或候選 | 品牌／型號已確定、目前在線 |
| 已辨識 | 有來源及理由支持某個身份或類型 | 必定有可用整合或已授權 |
| 建議接入 | 有證據支持某個整合選項或 HA 已提供候選 | 設定成功、所有功能皆支援 |
| 已授權 | 目前身份與授權允許特定讀取、設定或動作 | 永久有效、可擴大到其他設備／操作 |
| 已驗證 | 指定時間、方法與範圍的檢查通過 | 其他功能、物理結果或未來狀態也已通過 |

D1 使用 HA 已提供的整合關係與探索候選。現行多來源辨識已附規則理由與證據強度；廠商 OUI 或主機名稱只是提示，不能單獨當成確定型號。無法合併或證據衝突時保留多個候選，讓後續來源補證。

驗證至少要分開「整合設定已存在」「HA 可讀取狀態」「特定能力可用」和「實體動作已確認」。API state 讀取不能升級為實體設備驗收。授權撤銷、來源變舊、整合卸載或設備失聯後，先前的驗證紀錄仍是歷史事實，卻不能繼續代表當前可用。

原生 HA 登入與配對、模型讀取資料的範圍、Controller 家庭寫入權限是不同授權。探索結果不會替使用者授權任何一項。後續動作驗證沿用既有精確提案、批准與讀回機制，並先確認所測功能及目標設備。

## Adapter 與信任邊界

所有設備名稱、服務宣告、廠商文字與來源回應都當成不可信資料。只投影需要的欄位、限制大小、以文字顯示；不回傳完整 config entry 設定、秘密、OAuth 資料或完整 flow context。原生設定連結由產品固定產生，不採用設備回報或模型生成的任意 URL。

HA registry 與 config flow 接點的相容性由獨立 adapter 檢查。不能因使用 REST／WebSocket transport，就宣稱其中每個內部命令都是永遠相容的公開介面。新增欄位可忽略；缺少必要語意時顯示來源不支援或不可用。詳見 [adapter 邊界](ADAPTERS.md)。

目前路由器匯入不登入路由器；後續直接 Hub／帳號 adapter 只取得對應來源需要的權限，憑證由受信任服務保管。已實作的直接 LAN 收集限定選定實體網路、固定方法、期限與速率；不把任意掃描或 shell 交給 Hermes／workers。來源文字不能變成新的工具權限或執行指令。

盤點收集在外層 Linux 的選定實體介面執行，本身不修改 VM 網路。HAOS 預設基本 NAT；0.10.0 另有明確選擇的有線家庭接入，保留管理網卡並增加家庭 NIC，再從 Supervisor／Core 讀回位址、adapter 與內部網址。這條路徑與盤點分開授權／核對；精確媒體及巢狀 VM 通路的工程結果見 [驗證紀錄](VERIFICATION.md)，實體網卡與家庭現場另驗。HA 能看見多少候選也受實際網路與整合影響，不能保證空白家庭初始化就能看見全屋設備，見 [家庭區網接入](HA_LAN.md)。

## 分段交付與驗收

| 階段 | 交付範圍 | 必須取得的證據 |
|---|---|---|
| D1：HA 探索快照 | Owner 唯讀 API、分來源狀態、既有設備頁提示、固定原生交接 | 合成資料與協定測試、身份／去密／降級測試、編譯介面測試；真 Core 相容性另記 |
| D2：多來源盤點 | 可插拔路由器／LAN／Hub／帳號來源、覆蓋範圍、來源身份與新鮮度 | 每個 adapter 的真實來源測試、同名不同設備與同設備多來源案例、斷線與資料過期案例 |
| D3：對話引導接入 | 有範圍的探索工具、必要登入／配對交接、可接續的設定進度 | 真帳號流程、撤權與中斷恢復、既有設定保留、不重複提交或誤認完成 |
| D4：逐能力驗證與持續盤點 | 分別確認讀取／控制能力，呈現新增、移除與需重新確認的項目 | 授權的實體設備測試、離線與恢復、觀測期限、E3 現場與長時間證據 |

D1 的必要案例包括：

- 空快照、未連接 HA 與某一來源失敗，均呈現實際範圍；其他來源不被一併清空。
- 多個同 domain 整合、同名設備與 Hub 子設備不被錯誤合併；無 state 的 registry entity 仍納入功能數，沒有 device 的 entity 仍計入來源筆數／digest，但不虛構所屬設備或獨立呈現。
- 待設定流程只形成候選；被忽略、完成或消失的流程以重新讀取結果為準，不以產品自己啟動流程補齊。
- 惡意名稱、額外欄位、畸形必要欄位、超量回應與含秘密的 flow context，不形成腳本、外部導航或未經投影的輸出。
- 非 Owner、失效身份與讀取期間撤權不能取得家庭快照；新增唯讀 API 不擴大 MCP 或家庭 policy。
- 讀取、刷新與原生交接不發出 HA 設定／設備寫入；不把 `loaded`、有 state 或已有設定呈現為物理驗證。

工程測試、真 Core／HAOS、真帳號和實體設備結果分開登錄於 [進度](v3/PROGRESS.md) 與相應證據。D1 完成只代表上述唯讀切片可用；目前多來源收集與對話分享／接續追蹤各有獨立工程證據；自主接入、直接帳號盤點、逐能力物理驗證與整屋持續運作仍按後續階段驗收。

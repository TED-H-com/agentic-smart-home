# Hermes／Runner／coding worker 架構審查

日期：2026-10-12。審查起點為 `90d3054`（0.5.0），本文列出的修正是本輪尚待整合的工作樹變更。以 `docs/v3/` 六份 Owner 原稿、Worker Protocol v1 和後續 CLI 先行 onboarding 指示為依據；不修改原稿、不使用真實雲端帳號、不執行家庭操作。

## 結論與範圍

Hermes 已使用真正 upstream `AIAgent`、獨立認證儲存與 product MCP；Runner 也會啟動真正的官方 CLI。然而目前可執行的是受限結構化推論與固定 onboarding assistance。**Plan v3 的 Host／Home 自主 research、改 code、跑 tests 並交付產物仍未接通，E1／E2 尚未完成。** 這是缺少產品功能，不能只寫成「等待帳號驗收」。既有 `docs/v3/PROGRESS.md` 對此是誠實的。

本輪先重現並修正 Runner 取消後遺留程序與配對回覆遺失；另確認 Runner 的 idle retention 有未解缺口。一般 coding 仍須保持 blocked，不能因本輪取消修正而解除隔離限制。

## 已確認並修正的缺陷

### R1：CLI leader 結束不等於整組程序已停止

舊 `Providers.stop` 只送程序組 TERM 並等待 leader；若子程序忽略 TERM，`/jobs/{id}/cancel` 仍會回 `cancelled` 並釋出 worker。實際 API→Broker→Providers→fork fixture 重現時，回覆之後子程序仍為 `/proc` state `S`。

修正在 [providers.py](../../runner/agentic_runner/providers.py)：記錄 owned leader 的 UID／PID／start time，後續只對身份符合的 pidfd 發訊號；TERM 後即使 leader 已退出，也凍結及 KILL 已確認的剩餘程序組，檢查沒有非 zombie 成員才承認停止。無法證明身份或停止時，持久記錄 `stop_unconfirmed`。 [app.py](../../runner/agentic_runner/app.py) 不再將該狀態改為 cancelled，後續排隊與新工作、登入／登出都拒絕進行；重啟保留隔離狀態。登入背景程序也須完成停止確認才公開 connected。

回歸涵蓋真正 TERM-ignoring 子程序、模擬 pidfd 拒絕後不得啟動下一 writer、隔離狀態重啟保留，以及 PID start time 不符時完全不發訊號。此處是受限 CLI 程序組的停止證據，**不是任意程式自行 setsid／逃離程序組的完整 sandbox 保證**。後續自主 coding 必須使用既定 cgroup／容器邊界與完整 workspace lease。

操作限制：目前沒有可信的 quarantine reconciliation／clear API。服務重啟遇到原 running 工作會保守隔離；不能把重啟當成已證明舊程序不存在。後續恢復流程須獨立取得容器／程序身份已失效的證據，再准許新的 writer，不能僅刪除狀態檔。

獨立複查 Controller 時又確認普通家庭任務的 CancelledError 分支丟棄 Runner `/cancel` 回覆，仍保存 `cancelled`。本輪同步修正 [Controller runner helper](../../controller/agentic_controller/runner.py)、家庭任務、主機查詢與 Gateway 直接 Host／Home 對話：只有 exact job 的 terminal acknowledgement 才承認停止，回覆遺失或 stop_unconfirmed 都保留既有 `needs_reconcile` 狀態及 `error_code=stop_unconfirmed`。Hermes Gateway 也保留 Coordinator 的停止結果。相同 idempotency retry、Store recovery 均不得把待核對工作重新送出；此變更沒有擴充共享狀態 enum。

另一項真程序複查確認：重複 `/cancel` 或取消 HTTP request 會再次取消同一 writer task，打斷已開始的停止確認，留下活子程序並造成永久 quarantine。修正為同一 writer 只接受一次取消、各請求以 shield 等待同一個 cleanup；請求斷線不傳播第二次取消。服務正常關閉也不重複取消正在清理的 task。兩項 regression 使用實際忽略 TERM 的 leader／child，確認停止後才回 cancelled、沒有 quarantine、重送維持相同結果。修正前兩項失敗保留於 [review-runtime-duplicate-cancel-before.xml](../../evidence/review-runtime-duplicate-cancel-before.xml)；修正後含 containers 的中間結果為 **26 passed，12.48 秒**，見 [review-runtime-duplicate-cancel.xml](../../evidence/review-runtime-duplicate-cancel.xml)。

### R2：配對成功但 HTTP 回覆遺失後無法恢復

原本第一次 `/pair` 已寫入 token hash 後，完全相同的重試會收到 409；installer 的配對檔也會在下一個 30 秒刷新移除。Controller 即使重啟，也不能在原配對碼有效時間內取回已建立的同一身份。

修正在 [app.py](../../runner/agentic_runner/app.py)：原期限內只有完全相同的 code hash、Controller ID、principal、protocol 可恢復。回傳相同 bearer，不旋轉或重置配對。bearer 由 private／0600 的獨立 48-byte seed 與固定請求導出；SQLite 仍只存 bearer hash，私有 seed 拒絕 symlink、錯誤 owner／permissions／length／hardlink。配對檔只保留原 fingerprint 與原 code hash 相符的一份，到原期限後移除；過期檔即使尚待下一次刷新也不能通過 API。

回歸涵蓋 Runner 重啟、超過原 30 秒刷新間隔後的同身份重試、原期限不延長、不同 Controller／principal／code、失效期限、竄改配對檔以及不安全 seed。Controller 的 lost-response 整合回歸由另一工作線維護。

交叉審查另發現私有 seed 若因損坏的匯入狀態變成 0600 FIFO，原本會在 regular-file 檢查前阻塞 `os.open`，使 API event loop 停住。這不是遠端或 CLI 可寫入 private 目錄的漏洞。最小修正加入 `O_NONBLOCK`，先開啟、以 fstat 拒絕非一般檔案，再讀取 seed。回歸使用獨立 API 子程序與 5 秒外部上限，避免測試本身掛死；修正前 timeout 證據見 [review-runtime-fifo-before.xml](../../evidence/review-runtime-fifo-before.xml)，修正後回覆 409，沒有建立 bearer。

## 尚未修正、已獨立重現的缺陷

### R3：Runner 在沒有新工作時持續提供超過 retention 的結果

位置：[app.py 的 prune／job 與 GET jobs](../../runner/agentic_runner/app.py)。`prune()` 只由新工作 POST 呼叫，硬編碼 7 天，讀取 `/jobs/{id}` 不會先過期；也沒有 Owner 將 retention 降至 1–6 天時的 Runner 同步契約。

使用真正 Broker、SQLite 與 ASGI API，放入建立於 8 天前的 succeeded 工作，沒有再建立新工作；authenticated GET 仍回 200 與其合成家庭結果。這是資料保留正確性缺陷，不是雲端／設備驗收限制。

必要修正與驗收：讀取與背景清理都應遵守已保存的期限；Controller 變更必須同步適用的 Runner；降低期限立即清除內容，增加期限不得讓舊內容復活；去除內容後仍保留有界的去重／失效記錄，避免舊 request 再執行。需加入 idle 超時、重啟、降低後再升高及 lost-response retry 案例。
